# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded and relevant | Read the candidate repro report's **Environment** section and compare its versions, OS/platform, runtime, release channel, and relevant configuration with the issue context and any target versions in the repo-facts block. | Pass when the report names enough of the actual execution environment to locate the behavior (at least the affected tool/library version and OS/platform, plus a runtime, driver, shell, browser, or other issue-specific dependency when relevant). If the tested version, platform, or configuration differs from the issue, the report explicitly says so and explains what that means for the result. A faithful environment that cannot reproduce passes when the difference is identified; a missing environment or a silent material deviation fails. | required |
| Steps are stranger-rerunnable | Read the repro report's **Steps** and any commands, inputs, fixtures, configuration, working-directory or starting-state notes, then compare them with the issue's trigger. Use the steps section of the evidence guide to locate the proof. | Pass when a stranger with the stated environment can follow the commands or concrete actions from a stated starting state to the attempted trigger without private files, an undisclosed repository, or an omitted issue-specific prerequisite. The steps must use the issue's actual syntax, input, layout, or configuration; a faithful cannot-reproduce attempt may pass when its attempted trigger is still explicit and complete. | required |
| Artifact shows the issue behavior | Read the repro report's observed output, logs, screenshots, measurements, or other artifacts and compare them with the issue's described failure and expected behavior. | Pass only when the artifact directly shows the reported behavior, or when a faithful attempt directly shows that the issue did not reproduce. A version banner, successful startup, unrelated error, control result alone, asserted diagnosis, or artifact for an adjacent trigger is not evidence of the issue. The conclusion must distinguish observed from expected behavior. | required |
| Outcome is honest about target and evidence | Read the report's conclusion/expected-vs-observed language, the claim comment, and the issue context. Check all stated version, platform, release-channel, code-state, and scope claims against the evidence actually shown. | Pass when the package says reproduced only when the shown artifact matches the issue, and says cannot reproduce when it does not; it names meaningful deviations and does not generalize beyond the tested environment or assert a root cause/fix without support. An evidenced cannot-reproduce is a pass. A confident reproduction of a different error, a silent old-version or configuration deviation, or a crash/generalization not shown by the artifact fails. | required |
| Communication follows intent and repo policy | Read the claim comment and reproduction comment, the repo-facts contribution/AI-policy text, and the **Comms** section of the evidence guide. | Pass when the claim identifies the issue's concrete behavior and states what the author will investigate or reproduce next without promising an unearned fix, date, or certainty; the repro comment states what was actually observed in specific terms. If the repository requires disclosure of AI assistance, at least one posted comment explicitly discloses it; if policy is silent or permissive without disclosure, no disclosure is required. Boilerplate me-too/assign-me text, unsupported guarantees, missing intent, or a required-but-absent disclosure fails. | required |

## Verdict rule

Accept when every required check passes. A required `unclear` is a failure because
evidence that cannot be verified is not ready to post. There are no preferred checks;
the verdict is `accept` only for a package that passes all five checks.
